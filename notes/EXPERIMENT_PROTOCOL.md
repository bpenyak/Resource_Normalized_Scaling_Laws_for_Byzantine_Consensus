| Параметр | Значення |

**Критично:** репозиторій має бути **публічним**. Для приватного — 2000 хв/міс,
чого не вистачить на повну матрицю.

### Ключове обмеження пам'яті

Besu JVM за замовчуванням бере багато heap. Для n валідаторів на 16 GB:

```
BESU_OPTS=-Xmx512m
--data-storage-format=BONSAI
--sync-mode=FULL
```

Безпечна стеля: **n = 13**. n = 16 — best-effort (job може впасти по OOM;
`fail-fast: false` у матриці це переживе).

## Протокол RNM (Resource-Normalized Measurement)

Проблема: 13 валідаторів на 4 ядрах — це не «13 вузлів мережі», а
«13 процесів, що б'ються за 4 ядра». Виміряне падіння TPS змішує
накладні витрати консенсусу з конкуренцією за CPU.

Розв'язання:

1. Кожен контейнер отримує **фіксовану квоту** `q` ядер (`cpus: 0.25` у compose,
   реалізується через cgroup CFS quota) **незалежно від n**.
2. Кожен контейнер отримує фіксований `mem_limit`.
3. Звітується нормована пропускна здатність `TPS~ = TPS / q`.
4. `q`-інваріантність показника `β` **тестується** (експеримент X2), а не
   постулюється.

Наслідок: абсолютні значення TPS малі і **не порівнюються** з
опублікованими бенчмарками. Усі твердження стосуються **показників**
`β`, `γ` та покриття інтервалів.

## X2. Тест q-інваріантності

| | |
|---|---|
| Фактори | `n ∈ {4, 7, 13}` × `q ∈ {0.20, 0.25, 0.33}` |
| Реплікацій | 3 |
| Аналіз | ANCOVA: `log TPS~ = a + b·log n + Σ dⱼ·1{q=qⱼ}·log n` |
| Гіпотеза | `H₀: d₂ = d₃ = 0` (частковий F-тест) |
| Вихід | `β̂(q)` для кожного `q`, p-value |
| Jobs | 9 × 3 = 27 |

Якщо `H₀` відхиляється — звузити діапазон `q`, у якому інваріантність тримається,
і чесно зазначити це в Limitations.

## X3. Клієнтський фактор γ, c*, θ

| | |
|---|---|
| Фактор | `c ∈ {1, 2, 4, 8, 16, 32, 64}` |
| Фіксовано | `n = 7`, `q = 0.25` |
| Реплікацій | 3 |
| Вихід | `γ̂`, `ĉ*`, `θ̂` |
| Jobs | 7 × 3 = 21 |

**Критично для генератора навантаження:** кожен із `c` відправників має
**власний акаунт і власний пул nonce**. Спільний nonce-лічильник — це саме той
однопотоковий бутилочний шийк, що обмежив статтю 2 на рівні 29 TPS.

## X3b. Емпірична перевірка теореми ідентифікованості

Не потребує нових прогонів — це **ре-семплінг** даних X1 + X3.

1. Мати повну факторну сітку `(n, c)` з X1 і X3.
2. Для `λ ∈ {0, 0.25, 0.5, 0.75, 1.0, 1.5}` вибрати підмножину точок,
   що лежать уздовж шляху `log c = λ·log n + μ`.
3. На кожній підмножині підігнати **однофакторну** модель `TPS = TPS₀·n^α`.
4. Порівняти отримане `α̂` з передбаченням `γ̂λ − β̂`.
5. Знайти точку зміни знаку: `λ = β̂/γ̂`.

Це і є експериментальне пояснення розбіжності 8–15× між статтею 1 і статтею 2.

## X5. Ін'єкція відмов і характеризація детектора

### ВАЖЛИВЕ ТЕХНІЧНЕ ОБМЕЖЕННЯ

Транспорт devp2p/RLPx у Besu **зашифрований**. TCP-проксі **не може**
вибірково відкидати саме повідомлення консенсусу — він бачить лише
зашифрований потік. Тому:

- Клас відмов чесно називається **«omission + duplication»**
  (строга підмножина візантійської поведінки).
- Equivocation (подвійне голосування) **не моделюється**.
- Це має бути явно зазначено в `11_limitations.tex`. **Не називати це Byzantine.**

### Механізм ін'єкції

Замість проксі — `tc netem` на вибраних контейнерах:

```bash
tc qdisc add dev eth0 root netem loss 20% duplicate 10%
```

Простіше за проксі, еквівалентне за ефектом, не потребує патчингу Besu.
`faults/byz_proxy.py` лишається як резервний варіант для per-peer контролю.

### Детектор

Besu надає JSON-RPC метод **`qbft_getSignerMetrics`**, що повертає
`proposedBlockCount` для кожного валідатора у заданому діапазоні блоків.

Алгоритм:
1. Опитувати `qbft_getSignerMetrics` кожні `w` блоків.
2. Очікувана частка пропозицій кожного валідатора = `1/n`.
3. Прапорець `Xᵢ = 1`, якщо фактична частка < порогу `τ_p`.
4. `B̂ = (1/n)·Σ Xᵢ`.

**Ground truth відома за побудовою** — ми знаємо, які саме контейнери
деградували. Звідси:
- `p_d` — частка деградованих валідаторів, які були позначені
- `p_f` — частка справних валідаторів, які були позначені хибно
- ROC / AUC — розгортка по порогу `τ_p`
- `ρ` — вибіркова кореляція індикаторів `Xᵢ` серед деградованих вузлів

Це **перші виміряні** значення для величин, які стаття 2 змушена була
припускати. Патчинг Besu не потрібен.

| | |
|---|---|
| Фактори | `ℓ ∈ {0, 10, 20, 25}%` × `n ∈ {7, 13}` |
| Реплікацій | 3 |
| Jobs | 8 × 3 = 24 |

## X6. Симуляція для великих n

Дискретно-подієва модель (SimPy) QBFT: три раунди обміну, `O(n²)` повідомлень,
калібрована на X1–X4 (затримка обробки повідомлення, пропускна здатність каналу).

Прогони: `n ∈ {20, 30, 50, 75, 100, 150, 200, 300, 500}`.

Симуляція **не подається як вимірювання**. Її роль — показати, що форма
`n^(−β)` зберігається за межами досяжного діапазону.

Виконується локально, не в CI (секунди).

## X7. Валідація покриття інтервалів

1. Калібрувати модель **тільки** на `n ≤ 9`.
2. Передбачити `n ∈ {13, 16}`, побудувати `PI₉₀` і `PI₉₅`.
3. Порахувати частку відкладених прогонів, що потрапили в інтервал.

Метрика — **покриття**, не середня похибка. Середня похибка нефальсифікована.

Нових прогонів не потребує.

## X8. Абляція вибору розміру мережі

Профіль: 30 млн голосів за 12 год, пік ≈ 2100 TPS.

Для кожної моделі порахувати рекомендований `n` і вартість:

| Модель | Що робить |
|---|---|
| Лінійна | ігнорує деградацію |
| Однофакторна `n^α` (стаття 1) | `α > 0` → передбачає зростання TPS з n |
| USL | `C(n) = n/(1 + σ(n−1) + κn(n−1))` |
| RNM + chance-constrained (ця робота) | `Algorithm 2`, вікно `[nmin, nmax]` |

Метрика: вартість надлишкового / недостатнього забезпечення.

Виконується локально.

## X9. Крос-платформна реплікація

**Навіщо.** Найсильніше заперечення рецензента: «це артефакт однієї
реалізації». Відповідь має бути експериментальною, не риторичною.

**Що саме перевіряється.** Theorem 1 — твердження про МНК, а не про Besu.
Отже, на іншому клієнті:

- `(β, γ)` **мають** відрізнятися — це властивості системи;
- пряма `α̂ = γλ − β` **не має** відрізнятися — це властивість оцінювача;
- точка зміни знаку має лишитися на `λ = β/γ` з новими коефіцієнтами.

Якщо пряма не відтворюється — під сумнівом модель `\eqref{eq:bifactor}`,
а не теорема. Це важлива різниця, і її треба явно написати в статті.

**Конфігурація.**

| | |
|---|---|
| Клієнт | GoQuorum (IBFT), той самий сімейний протокол |
| Фактори | `n ∈ {4, 7, 13}` × `c ∈ {1, 4, 16, 64}` |
| Реплікацій | 2 |
| Jobs | 12 × 2 = 24 |

**Обмеження.** `qbft_getSignerMetrics` — специфічний для Besu метод.
Тому X9 покриває **лише пропускну здатність** (аналог X1 + X3), не детектор.
Це треба зазначити в Limitations, а не замовчувати.

**Що змінити в коді.** `gen_network.py` наразі викликає
`besu operator generate-blockchain-config`. Для GoQuorum потрібен окремий шлях
генерації genesis (`istanbul-tools` або статичний genesis із заданим
списком валідаторів). Це єдина реальна робота в X9.
